# BorderlessOS — Business Rules 01: Customer and Beneficiary Validation

**Project:** BorderlessOS — Cross-Border Remittance & Compliance Operations Platform  
**Project phase:** Day 1 — Step 4: Business Rules & Exception Handling  
**Specification ID:** BR-01  
**Status:** Approved  
**Scope:** Five-day educational MVP

## 1. Purpose and scope

BR-01 defines the rules for creating, viewing, updating, and deactivating customer bank-account beneficiaries in BorderlessOS.

BorderlessOS is an educational prototype, not a licensed financial product or certified compliance system. It must not move, custody, disburse, or settle real funds. Beneficiary validation in this specification is application-level data validation only; it does not prove that a real recipient or bank account exists.

## 2. Approved product decisions

- **Beneficiary type:** Bank-account beneficiaries only. Mobile-wallet beneficiaries are out of scope.
- **Field set:** Minimal — recipient name, destination country, destination currency, and fictional account/routing reference.
- **Deactivation:** Soft deactivation. Preserve the beneficiary record and its history; do not physically delete it.
- **Additional requirements:** None.

## 3. Beneficiary data model

| Field | Requirement | Validation / behaviour |
|---|---|---|
| `id` | Required | Generated by the system. |
| `customerId` | Required | Derived from the authenticated customer context. Never trust a client-supplied `customerId` as authoritative. |
| `recipientName` | Required | Must not be blank after trimming whitespace. |
| `destinationCountry` | Required | Must be a supported country code from the application's configured allowlist. |
| `destinationCurrency` | Required | Must be a supported currency code and permitted for the selected destination under the prototype configuration. |
| `accountReference` | Required | Fictional account/routing reference suitable for the prototype; validate against the configured prototype format. |
| `status` | Required | `ACTIVE` or `INACTIVE`. |
| `createdAt` | Required | Set by the system. |
| `updatedAt` | Required | Updated by the system when the record changes. |

No relationship field, nickname, mobile-wallet destination, or real banking verification is required for this MVP.

## 4. Business rules

### BR-01.1 — Customer ownership

A customer may create, view, update, and deactivate only their own beneficiaries. The backend must enforce ownership for every operation; hiding another customer's records in the user interface is insufficient.

### BR-01.2 — Required fields and server-side validation

Recipient name, destination country, destination currency, and fictional account/routing reference must be present and valid. Reject blank strings, whitespace-only values, unsupported codes, malformed values, and other invalid input on the server. Client-side validation may improve usability but does not replace backend validation.

### BR-01.3 — Supported destination

Country and currency must be selected from configured application allowlists. The selected currency must be permitted for the selected country according to the prototype's configuration. This is an application rule for the educational prototype, not a statement about real-world remittance eligibility or legal requirements.

### BR-01.4 — Soft deactivation

Deactivation changes the beneficiary status to `INACTIVE`; it does not physically delete the record. Inactive beneficiaries remain available for historical transfer references but cannot be selected for new transfers.

### BR-01.5 — Historical integrity

Existing transfers must retain their original beneficiary reference and relevant recipient/destination details captured at submission. Editing or deactivating a beneficiary must not silently rewrite a submitted transfer's history.

**Implementation note:** Preserve a submission-time snapshot of relevant beneficiary details on the transfer, rather than relying exclusively on the beneficiary's current mutable record.

### BR-01.6 — Synthetic data only

Use clearly fictional account/routing references in demo data. The application must not imply that these references have been verified by a bank, financial institution, or payment network. Real bank-account details are not required.

## 5. Edge cases and expected behaviour

| Scenario | Expected behaviour |
|---|---|
| Recipient name is missing or contains only whitespace | Reject with a field-validation error. |
| Country or currency is unsupported | Reject; do not create the beneficiary. |
| Country/currency combination is not allowed by the prototype configuration | Reject with a clear validation message. |
| Account reference is missing or malformed | Reject according to the configured prototype format. |
| Customer attempts to access another customer's beneficiary ID | Deny access without exposing the other customer's data. |
| Customer selects an inactive beneficiary for a new transfer | Reject submission server-side. |
| Customer deactivates a beneficiary with existing transfers | Mark it inactive while preserving historical references and details. |
| Customer edits beneficiary details after submitting a transfer | Preserve the submitted transfer's historical details. |
| Customer attempts permanent deletion | Do not expose permanent deletion in the MVP. |
| Customer requests deactivation of an already inactive beneficiary | Return a consistent result; do not corrupt the record. |
| Client bypasses UI validation | Backend validation must still reject invalid input. |
| A creation request is retried | Where idempotency is implemented, avoid duplicate creation; otherwise return a clear, consistent result and do not silently create duplicates. |

## 6. Proposed API behaviour

These endpoints are proposals for the Spring Boot backend and are not yet implemented.

| Method | Endpoint | Purpose |
|---|---|---|
| `POST` | `/api/v1/beneficiaries` | Create a beneficiary. |
| `GET` | `/api/v1/beneficiaries` | List the authenticated customer's beneficiaries. |
| `GET` | `/api/v1/beneficiaries/{id}` | Retrieve an owned beneficiary. |
| `PATCH` | `/api/v1/beneficiaries/{id}` | Update permitted beneficiary details. |
| `POST` | `/api/v1/beneficiaries/{id}/deactivate` | Soft-deactivate a beneficiary. |

### API and security requirements

- Derive ownership from authenticated identity; do not accept client-supplied `customerId` as authoritative.
- Enforce ownership and status rules in the backend for every applicable operation.
- Do not permit a new transfer to use an inactive beneficiary.
- Return consistent, understandable validation and authorization errors.
- Do not expose permanent deletion as an MVP operation.

## 7. Acceptance criteria

BR-01 is implemented when all of the following are true:

- [ ] A customer can create a beneficiary using the four required business fields.
- [ ] The backend validates required fields and supported country/currency combinations.
- [ ] A customer cannot read or modify another customer's beneficiary.
- [ ] An active beneficiary can be deactivated without deleting its record.
- [ ] An inactive beneficiary cannot be used for a new transfer.
- [ ] Existing transfer history remains unchanged when beneficiary details are edited or the beneficiary is deactivated.
- [ ] Validation and authorization failures return consistent, understandable API errors.
- [ ] Seed data and demo workflows use fictional account references.

## 8. Out of scope and safety boundaries

- Mobile-wallet beneficiaries.
- Permanent deletion of beneficiary records.
- Verification that a real recipient or bank account exists.
- Real bank-account validation or real payment-network verification.
- Real fund movement, custody, disbursement, or settlement.
- Claims that the prototype determines real-world remittance eligibility or certifies compliance.
